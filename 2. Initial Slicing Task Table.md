  (`drops.dagstuhl.de`) whose `robots.txt` only disallows a few API/
  metadata paths, none of which cover the actual file downloads. Used
  that instead. Real files in hand:
  - `data/dblp.dtd` (13 KB) — downloaded in full, from
    `drops.dagstuhl.de/storage/artifacts/dblp/xml/2023/dblp-2023-06-28.dtd`.
  - `data/dblp.xml.gz` — the real September 2026 monthly release

- `jobs/dblp_xml.py`: the shared constant-memory streaming reader (DATA-1),
  used by both the profiler and (later) the ETL job so the two never
  drift. **Real bug found and fixed while building this**: `lxml`'s
  `iterparse` (v6.1.3) has no `parser=` argument at all, and a custom
  `Resolver` registered on the global default parser is never consulted
  for iterparse's own internal DTD loading — both are dead ends. What
  actually works, confirmed by direct experiment: `load_dtd=True` +
  `resolve_entities=True` alone, with a file literally named `dblp.dtd`
  sitting next to the `.xml.gz` on disk — libxml2 resolves the DOCTYPE's
  relative `SYSTEM "dblp.dtd"` against the `.xml.gz`'s own on-disk path.
  This is exactly the proposal's own DATA-1 wording ("keeping dblp.dtd
  next to it") taken literally, not a workaround.
- `jobs/profile_dblp.py`: DATA-2 through DATA-6 all implemented — type/
  year counts, field completeness, authors-per-paper and papers-per-author
  distributions (keyed by dblp's own `pid` attribute when present, falling
  back to name text), top-50 venue prefixes, homonym-suffix and `pid`-
  coverage checks for DATA-5, and a `suggest_data_scope()` heuristic for
  DATA-6 that greedily ranks venues by paper count per candidate start
  year until the 300k–800k target band is hit.
  **Two more real bugs found via the unit tests, both fixed**: `proceedings`
  records (venue containers, not authored papers) were being counted into
  the author/field-completeness/authors-per-paper stats, dragging down
  "% records with an author" for no real reason; and `www` (person) record
  keys like `homepages/1/1000` were leaking into the venue-prefix ranking
  meant for real venues like `conf/kdd`. Both fixed by giving `proceedings`
  and `www` their own explicit branches in `profile()` instead of falling
  through the generic path.
- `jobs/tests/test_profile_dblp.py`: 11 unit tests against a small,

  `sample.dtd`) covering every DATA-2..6 stat, entity resolution, the

  author name and title read, across `dblp_xml.py`, `etl.py`, and
  `profile_dblp.py`; confirmed fixed directly against the real failing
  record (`conf/sigir/SchmittCS02`) and covered by a regression test that
  reconstructs the exact `_Entity`-node tree, since a small fixture can't
  otherwise reproduce it (`jobs/tests/test_dblp_xml.py`). Full details and
  the real before/after impact on distinct-author counts are in
  `reports/dblp_profile.md`. Required a full ETL reload after the fix —
  see the updated real counts below.

## P3 — OpenAlex enrichment

**Status: DONE (2026-09-27).** Covers DB-3 (§8.1).

- **Real, non-obvious finding that reshaped the whole design:** the live
  OpenAlex API returns `X-RateLimit-Limit: 1000` / `X-RateLimit-Remaining` /
  `X-RateLimit-Reset` headers - a **credit budget** (1 request = 1 credit,
  regardless of how many DOIs are batched into that request's filter) over a
  multi-hour reset window, not the unlimited/simple-throttle "polite pool"
  the proposal's own text assumed. Confirmed empirically (not from docs -
  `WebFetch` to OpenAlex's own docs failed in this environment): three
  successive real requests showed `Remaining` dropping 996 → 995 → 994,
  1-for-1. With 229,584 DOI'd papers needing 50-DOI batches, a full pass
  needs ~4,592 requests - about 4.6x a single window's budget.
  - **Redesigned the job around this real constraint** instead of pretending
    a one-shot full pass was possible: `jobs/enrich_openalex.py` only
    processes `WHERE doi IS NOT NULL AND abstract IS NULL`, so a later run
    (once credits reset) automatically continues from wherever an earlier
    run stopped, rather than reprocessing or requiring separate bookkeeping.
  - Reads the real `X-RateLimit-Remaining` header after every request and
    stops gracefully well before it would trip the limit (a `RateLimitStop`,
    not an error), plus a hard `max_requests` cap as a second line of
    defense and 429/`Retry-After` handling for belt-and-suspenders safety.
  - Writes are additive (`UPDATE ... WHERE abstract IS NULL`,
    `INSERT ... ON CONFLICT DO NOTHING`) rather than P2/P5's truncate-and-
    swap, since this job is explicitly designed to be extended by later
    runs, not to fully replace its own prior output each time.
  - **Citation edges can only be discovered between two papers this job has
    *both* actually fetched** in some run: a referenced work is identified
    by an opaque OpenAlex id, not a DOI, so there's no way to know it's "one
